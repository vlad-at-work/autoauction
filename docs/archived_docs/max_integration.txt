Секция 1 — Сравнение возможностей (MAX vs Telegram)

Использование токена бота:

MAX: После регистрации чат-бота в кабинете организации платформа выдаёт токен. Он используется для аутентификации API-запросов: передается в HTTP-заголовке Authorization при обращениях к Bot API MAX. Токен даёт права на отправку сообщений, получение обновлений и управление ботом через Platform API (раньше botapi.max.ru, теперь platform-api.max.ru). Например, запросы GET /me (проверка токена), POST /messages (отправка сообщения) требуются отправлять с этим заголовком. В MAX нельзя передавать токен в URL – только через заголовок (это обновление правил с 2025 года). Тот же токен используется косвенно для безопасности WebApp: при запуске мини-приложения формируются подписанные данные initData, где проверка подписи выполняется с учётом секретного ключа на основе Bot Token.

Telegram: Токен бота (выдаётся BotFather при создании бота) используется для вызова методов Telegram Bot API. В отличие от MAX, Telegram включает токен в URL запросов (пример: https://api.telegram.org/bot<Токен>/sendMessage) или допускает передачу как параметр при установке вебхука. Токен даёт доступ к методам отправки сообщений, настройки вебхука, получения обновлений (getUpdates), редактирования сообщений и пр. Права токена стандартные: можно отправлять сообщения в личный чат с пользователем или группу, где бот присутствует, получать обновления о входящих сообщениях, управлять меню и командами бота, и т.д. Разрешения на определённые действия (например, чтение всех сообщений в группе) зависят от настроек бота (флаги privacy mode). В контексте мини-приложений токен тоже служит секретом для проверки подписи переданных данных – например, Telegram генерирует hash (в initData) на основе HMAC с использованием SHA256(bot_token).

Идентификаторы пользователя и чатов:

MAX: Каждый пользователь имеет уникальный user.id (64-битное число) в экосистеме MAX. Если мини-приложение открыто из личного чата бота с пользователем, в стартовых параметрах WebApp передаются данные чата: объект chat с chat.id и chat.type. В приватном диалоге chat.id, по сути, соответствует идентификатору диалога с ботом – его можно использовать для отправки сообщений этому пользователю. (Вероятно, chat.id совпадает с user.id для приватных чатов, но в группе будет другой ID.) Для групповых чатов chat.type будет "CHAT" (в отличие от "DIALOG" для личных). У бота есть свой собственный user_id (отвечает за него метод /me), но для рассылки сообщений пользователям используются их chat_id. Важно: чтобы бот смог отправить уведомление, пользователь должен иметь открытый диалог с ботом (см. ниже про согласие) – иначе платформа не позволит доставить сообщение.

Telegram: У каждого пользователя тоже есть глобальный id (целое число до ~10¹⁰). В Bot API приватный чат между ботом и пользователем идентифицируется тем же user_id пользователя (передается как chat.id для личного чата). У группы или канала свой уникальный chat_id (отрицательные для супергрупп/каналов, но концептуально это просто ID чата). Бот может отправлять сообщения по этому chat_id. Внутри WebApp Telegram в объекте Telegram.WebApp.initDataUnsafe также передаётся объект user (с id, username, именем) и, при запуске из группы, объект chat с id, type (group, supergroup и т.п.). Обратите внимание: Telegram не позволяет боту писать пользователю, пока тот явно не запустил бота (не нажал «Start»). То есть даже зная user_id, сначала нужно получить от пользователя любое входящее сообщение/команду, чтобы бот мог отправлять уведомления.

Передача данных мини-приложению и идентификация пользователя:

MAX: Когда пользователь открывает мини-приложение в MAX, в него автоматически передаются стартовые параметры – строка initData в URL, содержащая информацию о пользователе, чате и пр., а также hash для проверки. Подключив JS-библиотеку MAX Bridge (<script src="https://st.max.ru/js/max-web-app.js"></script>) вы получаете глобальный объект window.WebApp. Через WebApp.initDataUnsafe доступен разобранный объект с параметрами запуска (WebAppData), включая user (данные профиля пользователя) и chat. Например, WebApp.initDataUnsafe.user.id даст ID пользователя, user.first_name и т.д. Эти данные можно использовать, чтобы идентифицировать пользователя без отдельного ввода логина. Также есть WebApp.initData (сырой URL-encoded стринг), которую нужно использовать при валидации на сервере. Мини-приложение в MAX может дополнительно запросить контактные данные пользователя (номер телефона) через метод WebApp.requestContact() – откроется системный диалог, и при согласии бот получит контакт. Однако по умолчанию номер телефона не передаётся, только базовая инфа из профиля. Для привязки аккаунта обычно достаточно знать постоянный user_id MAX – его можно хранить в базе как связку.

Telegram: Аналогично, при запуске Web App в Telegram, страница получает объект window.Telegram.WebApp (после подключения <script src="https://telegram.org/js/telegram-web-app.js"></script>) . В нём есть Telegram.WebApp.initDataUnsafe с полями user (id, first_name, last_name, username, language_code, и т.д.) и chat (если запущено из группы). Также приходит hash для проверки и auth_date. Эти параметры передаются через строку в URL (доступна как Telegram.WebApp.initData). В Telegram тоже можно не требовать отдельной регистрации: ID и имя пользователя уже известны и подтверждены платформой. При необходимости можно запросить номер телефона – но у Telegram нет прямого requestContact в WebApp. Вместо этого бот может отправить кнопку с запросом контакта (тип KeyboardButton.request_contact), либо использовать виджет входа (Telegram Login Widget) вне контекста WebApp. В рамках Mini App, как правило, достаточно initData для аутентификации пользователя.

Проверка и доверие к переданным данным:

MAX: Данные initData подписаны платформой MAX, и обязательно должны быть провалидированы на вашем бэкенде перед использованием. Алгоритм проверки (HMAC SHA-256) описан в документации: нужно собрать все переданные пары key=value (кроме самого hash), отсортировать по ключам, соединить символом \n. Затем вычислить secret = HMAC_SHA256("WebAppData" + BotToken) и my_hash = HMAC_SHA256(secret, data_string). Если hex(my_hash) совпадает с полученным hash – данные подлинные. Ваш сервер, зная токен бота, может это сделать; злоумышленник без токена – нет. Таким образом, поля user.id, user.username и др., можно доверять только после валидации. (В противном случае пользователь мог бы открыть ваш веб без мессенджера и подделать параметры.) Кроме подписи, проверяйте auth_date – например, отклоняйте слишком старые запросы, чтобы избежать replay-атак. MAX передаёт время auth_date (Unix-time) в данных. Платформа MAX требует, чтобы вы реализовали эту проверку – отсутствие валидации initData является причиной для провала модерации приложения.

Telegram: В Telegram механизм практически тот же: присутствует поле hash и auth_date в initData. Документация рекомендует на сервере отсортировать все поля (кроме hash) и проверить HMAC-SHA256 подпись, используя SHA256(bot_token) как секрет. Если подпись корректна – пользователь действительно тот, за кого себя выдаёт. Нельзя пропускать эту проверку: официальный блогеры подчёркивают, что без валидации любой может подставить чужой ID и выдавать себя за другого. Таким образом Telegram WebApp может выступать как своего рода OAuth: после успешной проверки у вас есть достоверный user_id Telegram, имя, юзернейм. Дополнительно стоит проверять свежесть auth_date (например, авторизация старше суток – неприменима). Telegram Login Widget (виджет входа) использует аналогичную схему подписи, но запускается вне Telegram-клиента; в контексте же Mini App пользовательские данные уже переданы. Итого: доверять initDataUnsafe на фронтенде нельзя, нужно отправить initData на свой сервер и проверить по алгоритму, прежде чем привязывать учетную запись.

Ограничения и возможности отправки сообщений:

MAX: Бот MAX может отправлять текстовые сообщения, а также файлы, изображения, и т.д. (поддерживается загрузка файлов через POST /upload и вложения в сообщениях). В сообщениях можно использовать форматирование (Markdown или HTML), упоминания пользователей, смайлы и т.д. Доступны inline-кнопки: MAX позволяет прикреплять к сообщению до 210 кнопок (30 строк по 7). Типы кнопок: callback (генерирует событие message_callback в обновлениях бота), link (открывает внешнюю ссылку), request_contact (запрос телефона), request_geo_location, open_app (открыть привязанное мини-приложение), message (послать заранее заданное сообщение боту). Например, кнопка типа open_app откроет мини-приложение прямо внутри чата MAX – это аналог кнопки WebApp в Telegram. Фоновые уведомления: отправлять сообщения без действий пользователя можно, но только после того, как пользователь начал диалог с ботом (открыл мини-app или написал сообщение). Принудительно «навязать» беседу бот не может. Также, у MAX есть ограничения по скорости: не более 30 запросов API в секунду на бот. Если превышать, вернётся ошибка 429. Конкретных лимитов «в час в чат» не указано, но стоит соблюдать разумные интервалы, чтобы не превысить 30 RPS и не раздражать пользователя.

Telegram: Telegram Bot API поддерживает широкий спектр сообщений: текст, фото, видео, документы, стикеры, локации, контакты, опросы, игровые анимации и т.п. – бот может отправлять их используя методы sendMessage, sendPhoto, sendDocument и т.д. Inline-кнопки (InlineKeyboardMarkup) также поддерживаются, включая специальные кнопки: callback_data (порождает CallbackQuery), url (открывает ссылку), web_app (открывает Web App по указанному URL), login_url (авторизует пользователя через бот), switch_inline и т.п. Максимальное число кнопок в строке – 8, количество строк не ограничено (но есть ограничение на общий размер разметки). Ограничения отправки: Telegram накладывает rate limit ~30 сообщений/секунда в сумме и ~20 сообщений/минуту на отдельный чат. Бот не может писать пользователю, пока тот не нажал «Start» или не отправил команду боту; также бот не может «добавиться» к пользователю сам – пользователь должен либо сам открыть бот, либо бот должен быть добавлен в групповой чат. После этого можно отправлять уведомления в любой момент. Telegram боты не могут звонить или отправлять системные уведомления вне чата. Если пользователь остановил бота или удалил диалог, дальнейшие сообщения не дойдут. В мини-приложении Telegram (WebApp) бот не получает события автоматически о запуске (если WebApp открыт через startapp-ссылку, бот получит команду /start с параметром). Для надёжного оповещения стоит при первом входе попросить пользователя нажать кнопку или как-то проявить активность, чтобы убедиться, что бот активен. Кроме того, Telegram запрещает массовую несанкционированную рассылку – убедитесь, что у вас имеется явное согласие (например, кнопка «Включить уведомления» внутри приложения).

Развёртывание и хостинг мини-приложений:

MAX: Мини-аппы MAX – это обычные веб-приложения, которые загружаются по HTTPS внутри мессенджера. Их нужно разместить на хостинге с SSL. Официально рекомендованы сервисы вроде Vercel или GitHub Pages для статических страниц. На этапе подключения в кабинете разработчика вы указываете URL приложения (пример: https://mydomain.com/app/index.html) . Домен должен быть доступен по HTTPS (HTTP не пройдёт) и соответствовать правилам (допустимые символы, длина ≤1024). После привязки мини-приложения к боту в чате появляется кнопка «Открыть» для запуска веб-приложения. CSP и sandbox: MAX открывает приложение внутри своего WebView – дополнительных требований CSP обычно нет, но если ваше приложение делает внешние запросы, убедитесь, что они разрешены (например, если API бекенд находится на том же домене или указан в Content-Security-Policy). Также желательно обслуживать все ресурсы (JS, картинки) с того же домена или с разрешённых CDN. Хранение данных пользователей: согласно законам РФ, персональные данные российских пользователей должны храниться на серверах в РФ. Поэтому бекенд (БД) лучше размещать в России. Временно можно разрабатывать с использованием иностранного хостинга (как упоминается, фронтенд можно на Vercel), но в продуктиве для соответствия 152-ФЗ ваш сервер и база (где хранится имя, телефон и др.) должны быть на российских площадках (например, Яндекс Облако, VK Cloud и т.д.).

Telegram: Telegram Web Apps можно хостить на любом HTTPS-домене, доступном публично. При регистрации основного приложения через BotFather вы указываете URL, на который будет ссылаться бот. Требования: действующий SSL-сертификат (не самоподписанный), иначе у пользователей может не загрузиться. Telegram не ограничивает явным списком доменов – вы можете использовать свой. Однако, чтобы воспользоваться виджетом входа (если вдруг), нужно привязать домен к боту через /setdomain у BotFather. В контексте WebApp это не строго обязательно, но рекомендуется (это включается автоматически при указании URL веб-приложения бота). Content Security Policy: Telegram открывает WebApp в встроенном браузере (на мобильных) или в новом окне (в веб-версии Telegram). Ваше приложение не находится в sandbox, у него полный контекст страницы. Но Telegram добавляет в запрос User-Agent специфичные заголовки, и можно проверить заголовок X-Frame-Options – он должен позволять загрузку (если вы не хотите, чтобы страница запрещала framing). Обычно, если просто хостить обычную страницу, проблем нет. Географическое хранение данных: Telegram – международная платформа, прямых требований хранить данные в РФ она не выдвигает. Но если ваш сервис попадает под российские законы, то та же 152-ФЗ применима: храните персональные данные (полученные от Telegram, например имя, ID, телефон) на серверах в РФ.

Секция 2 — Архитектура end-to-end для потока

Сценарий «Лэндинг → Мессенджер → Уведомление» (MAX): Пользователь заходит на ваш сайт и нажимает кнопку «Войти через MAX». Предположим, у него установлен мессенджер MAX на телефоне или открыта web-версия. Кнопка содержит глубокую ссылку вида https://max.ru/<BotName>?startapp=<state> . Шаги следующие:

Переход из сайта в MAX: По нажатию ссылки система предлагает открыть приложение MAX (на мобильном автоматически, на ПК может открыться веб-версия MAX в браузере). Пользователь подтверждает – открывается чат с вашим ботом в MAX, и сразу запускается привязанное мини-приложение. Если бот ещё не был добавлен, он добавляется (но в MAX боты доступны только через каталог для организаций, поэтому обычно пользователь уже добавил бота или переходит по приглашению).

Запуск мини-приложения: Встроенный веб-браузер MAX загружает URL вашего приложения. При запуске MAX передаёт в URL параметры startapp (если были в ссылке) и WebAppData с данными пользователя. В вашем фронтенде на стороне клиента сразу доступен объект window.WebApp с полями initDataUnsafe.user, initDataUnsafe.chat и т.д. – вы узнаёте, кто пользователь (ID, имя) и контекст. Интерфейс MAX сначала показывает «скелетон»-заглушку; ваш код должен вызвать WebApp.ready() когда интерфейс готов.

Аутентификация пользователя внутри мини-приложения: Если у вас собственная учётная запись (например, аккаунт на вашем сервисе), нужно привязать к ней данного пользователя MAX. Здесь возможны варианты: (a) авторизация по данным мессенджера – т.е. создать локальную учётку на основе user.id MAX и считать пользователя вошедшим без отдельного логина; (b) если требуется, запросить у пользователя дополнительную информацию, например номер телефона (можно через requestContact() диалог) или попросить войти в существующий аккаунт вашего сервиса (например, по паролю или коду). Но раз цель – упростить через мессенджер, обычно выбирают первый путь. Ваше мини-приложение может отправить на ваш бекенд AJAX-запрос (например, POST /auth/max/callback) с полученным initData (или уже разобранным user.id + hash) и любыми доп.данными. Бекенд проверяет подпись и вытаскивает user_id. Далее бекенд ищет в БД пользователя с привязкой к этому MAX ID. Если находит – авторизует под ним, если нет – регистрирует нового (создаёт запись пользователя и связь). Возвращается, например, сессия или JWT для мини-приложения. В итоге внутри WebView пользователь считается вошедшим в ваш сервис, а ваша система помнит связку аккаунт ↔ MAX.

Сохранение связки и согласие на уведомления: На сервере стоит таблица, которая хранит связь пользователя с мессенджером (см. модель ниже). После логина вы создаёте запись: user_id (ваш внутренний), max_user_id (ID в MAX), max_chat_id (ID чата с ботом для отправки сообщений), статус подписки (активна/отключена) и пр. Замечание: В MAX chat_id для личных сообщений обычно равен user_id – но лучше сохранить явное значение из initData. Теперь, чтобы отправлять этому человеку уведомления, нужен его явный согласие. Предположим, внутри мини-приложения вы показываете кнопку «🔔 Получать уведомления». Пользователь нажимает её – ваше приложение может отправить запрос на сервер (POST /notifications/enable например). Вы отмечаете в БД, что данный пользователь подписан. (В контексте MAX, наличие диалога уже означает техническую возможность слать сообщения, но явное согласие полезно с точки зрения UX и требований: пользователь осознанно подписался). После этого ваш сервер через Bot API MAX может отправить приветственное сообщение пользователю, подтверждая подключение. Например, вызвать POST /messages с телом { "chat_id": <max_chat_id>, "text": "Нотификации включены ✅" } и заголовком Authorization с токеном. Бот доставит сообщение в MAX: пользователь увидит в чате сообщение от бота («Нотификации включены»).

Дальнейшие уведомления: Когда ваше основное приложение хочет отправить пользователю уведомление (шаг F), оно обращается к модулю уведомлений, передаёт идентификатор пользователя или событие. Этот модуль у вас узнаёт, что у пользователя есть привязка MAX с chat_id и активной подпиской, и вызывает Bot API MAX для отправки сообщения. Обычно реализуется отдельный внутренний метод или сервис “Notifier”, который инкапсулирует логику: для каждого подписчика формирует текст и вызывает API мессенджера. Например, POST https://platform-api.max.ru/messages с JSON { "chat_id": ..., "text": "Ваша ставка выиграла аукцион!" }. Если нужен более сложный контент (картинки, кнопки) – формируется payload с attachments. Бот MAX отправляет сообщение. Пользователь получает его в мессенджере как обычное сообщение от бота.

Сценарий «Лэндинг → Мессенджер → Уведомление» (Telegram): Здесь процесс похож, но с нюансами Telegram:

Переход в Telegram: Пользователь на сайте кликает «Войти через Telegram». Ссылка имеет вид https://t.me/<BotUsername>?startapp=<payload> . Если Telegram установлен на устройстве, ссылка его откроет и сразу откроет диалог с ботом и запустит Web App внутри него. Если Telegram веб-клиент – откроется новый вкладка Web Telegram. Обратите внимание: при первом обращении к боту пользователь, скорее всего, должен нажать кнопку «Start». Telegram не запускает бота абсолютно без действия: обычно при переходе по start/startapp ссылке появляется окно чата с ботом и синяя кнопка «Запустить». Пользователь нажимает её – тем самым посылается команда /start вашему боту (с параметром, если был указан). Это действие необходимо, чтобы бот смог дальше слать сообщения. Можно встроить startapp ссылку так, чтобы Telegram-клиент сразу открыл веб-приложение (в последних версиях Telegram это происходит после нажатия «Start», иногда – сразу, в зависимости от клиента). В результате: у пользователя открыт чат с ботом (бот помечен как «started») и поверх него – ваш Web App.

Запуск Web App и получение данных: В открывшемся Telegram Web App ваше приложение получает через window.Telegram.WebApp.initDataUnsafe информацию о пользователе: id, имя, username, language_code и т.д., а также tgWebAppStartParam (если вы передавали payload). Если запуск из приватного чата – chat_type будет “private”, если из группы – “group” и т.п. (В данном сценарии, скорее всего, это приватный чат). Telegram обеспечивает, что бот уже получил событие /start с тем же параметром, так что на вашей стороне сервер тоже знает, кто подключился (из webhook getUpdates).

Авторизация пользователя через Telegram: Так же, как с MAX, вы на фронте отправляете initData на свой сервер для проверки. Например, POST-запрос на /auth/tg/callback с телом initData. Бекенд рассчитывает подпись (используя токен бота) и сверяет с hash. При успехе получает id пользователя Telegram. Затем происходит поиск или создание локального аккаунта, привязка Telegram ID к вашей учётной записи. Telegram также предоставляет username (если есть) – можно сохранить для отображения, и first_name/last_name. Телефон не передаётся – при необходимости можно попросить в WebApp ввести или нажать кнопку в чате: например, бот может прислать клавиатуру с кнопкой «📱 Share Phone» (это не внутри WebApp, а обычная KeyboardButton, пользователь нажмёт – бот получит update с Contact). Но чаще всего достаточно идентификатора, а при необходимости связать с профилем – можно по username или запросить ввод email. Предпочтительный сценарий – бесшовный вход без пароля: раз Telegram подтвердил личность, вы либо создаёте нового пользователя на лету, либо логините существующего (например, если заранее связали Telegram ID с аккаунтом). После этого возвращаете Web App’у сессию (например, куку с session_id или JWT). Визуально внутри Telegram Mini App пользователь может увидеть что «вход выполнен».

Согласие на уведомления: Telegram требует, чтобы пользователь сам инициировал общение. Раз он нажал Start, бот уже имеет право писать. Но дополнительным жестом в UI можно попросить пользователя нажать «Получать уведомления». В WebApp можно показать кнопку, при нажатии которой ваш фронтенд дергает ваш бекенд (/notify/enable). Бекенд помечает подписку в БД (сохраняет telegram_user_id и chat_id пользователя, статус «subscribed»). Технически, если бот запущен, chat_id = user_id, и этого достаточно. Можно сразу послать тестовое сообщение: вызвать метод Bot API sendMessage с chat_id и текстом «Уведомления подключены». Telegram отправит сообщение пользователю в чат с ботом. (Если бот использует webhook, этот sendMessage – просто HTTPS-запрос к api.telegram.org.) Пользователь увидит сообщение от бота в том же чате, где открыт WebApp.

Отправка уведомлений: Когда нужно уведомить пользователя, ваш сервер формирует текст (или другие медиаданные) и вызывает метод sendMessage (или др.) Telegram Bot API с нужным chat_id. Проще говоря, у вас есть фоновый джоб или триггер, который для каждого подписанного пользователя выполняет POST https://api.telegram.org/bot<Токен>/sendMessage с JSON {"chat_id": <tg_chat_id>, "text": "..."} . Telegram мгновенно доставляет сообщение. Если пользователь в этот момент в Telegram – увидит нативное уведомление. Если он отключил бот или удалил – вы получите ошибку от API (например, 403 Forbidden: bot was blocked by the user). Обработку таких ошибок стоит реализовать: при блокировке вы отмечаете пользователя как отписавшегося. (Замечание: Telegram Login Widget – альтернативный способ – мог бы авторизовать на сайте без запуска бота, но тогда бот не сможет писать, пока пользователь не запустит. Поэтому для потока «уведомления» WebApp подход лучше.)

Проектирование бэкенда и интеграция: Рекомендуется создать отдельные endpoints (маршруты) для обработки взаимодействия с каждым мессенджером:

/webhook/max – endpoint, который вы укажете при регистрации вебхука MAX-бота. MAX будет слать POST-запросы с событиями (JSON). Ваш код должен разобрать req.body: это объект Update. В нём может быть message_new (новое сообщение от пользователя), message_callback (нажатие inline-кнопки), message_event (например, открытие мини-приложения?), и т.п. Вы должны отправлять в ответ HTTP 200 быстро (иначе MAX может отключить вебхук за таймаут). Если бот в чате получил /start или другое – здесь нужно обработать. Например, на /start можно сразу отправить приветствие (через API отправки, не путать с HTTP ответом) или просто зафиксировать, что пользователь активировал бота. В MAX, как и в Telegram, вы можете выбрать вместо вебхука Long Polling: тогда endpoint /webhook не нужен, а ваш сервер/скрипт периодически делает GET /updates. Но для production вебхук предпочтительнее.

/webhook/tg – аналогично, webhook для Telegram. Вы устанавливаете его через setWebhook метод Bot API. Telegram будет посылать POST с JSON Update на этот URL. Там важны поля: message (если новое сообщение), callback_query, web_app_data (если пришли данные из WebApp через sendData, хотя для direct WebApp Telegram не шлёт их напрямую) и т.д. Опять же, надо ответить 200 быстро. Если бот получил команду /start – здесь можно обработать (например, приветствовать или учесть реферальный параметр). Примечание: для Telegram не обязательно иметь вебхук – можно опросом getUpdates. Но webhook надёжнее и быстрее для масштабов.

/auth/max/start – может использоваться, если вы инициируете авторизацию через браузер. В данном сценарии не очень нужен, так как мы открываем мини-app сразу. Но теоретически мог бы перенаправлять на max.ru/…?startapp=.... В рамках WebApp, скорее, не нужен.

/auth/max/callback – endpoint, на который мини-приложение MAX отправляет данные для логина. Например, фронт может сделать POST /auth/max/callback с телом { initData: "...", phone: "..." }. Здесь ваш сервер валидирует initData и создаёт сессию. Можно сразу выставить cookie с сессионным ID, потому что WebView MAX в мобильном – это отдельный контекст (cookie там изолированы от обычного браузера, но сохраняются между запусками одного и того же домена). Либо фронт ждёт JSON {token: ...} и сохраняет его в localStorage.

/auth/tg/callback – аналогично для Telegram WebApp. Туда прилетит initData. Обработка схожа: проверить, залогинить пользователя. Telegram Web Apps позволяют вместо callback использовать встроенный способ: если бэк сгенерирует JWT, можно вызвать Telegram.WebApp.close() и передать этот токен через WebApp.url фрагмент – но обычно проще завершить внутри.

/notify (возможно, /notify/send) – внутренний endpoint или метод вашего приложения, куда бизнес-логика отправляет события для нотификаций. Например, когда в вашем приложении происходит событие (новое сообщение, ставка выиграна), вы делаете вызов POST /notify с параметрами (user_id, текст или шаблон). Этот endpoint смотрит, какие мессенджеры привязаны у пользователя: если есть MAX – отправляет через MAX Bot API, если есть Telegram – через Telegram Bot API, и т.д. Реально можно и без отдельного URL – код вызовет соответствующий сервис.

Модель данных (реляционная схема) для хранения привязок: Вам нужно хранить пользователей и их связки с ботами. Минимально можно иметь таблицы:

users – основные данные аккаунта на вашем сервисе (id, имя, email/телефон, hash пароля или если только через мессенджер – можно без пароля, etc.).

messenger_links (или user_providers) – связь пользователь ↔ бот. Поля:

id (первичный ключ),

user_id (внешний ключ на users),

provider (строка: "MAX" или "Telegram"),

provider_user_id (идентификатор пользователя в мессенджере; для Telegram – их user_id, для MAX – user.id из WebAppData),

chat_id (идентификатор чата для отправки сообщений: для Telegram обычно совпадает с user_id, для MAX – может совпадать с user_id либо быть тем же значением chat.id),

username (опционально – username в телеграме или MAX для информации),

auth_date (время, когда привязка подтверждена, UNIX timestamp),

is_notifications_enabled (булево, флажок согласия),

created_at, updated_at.

(Можно добавить init_data_hash или nonce, но если проверили и сохранили auth_date, повторное использование не страшно.)

Возможно, таблица notifications – очередь уведомлений, если нужно гарантированно доставлять (но можно и сразу слать).

Если предполагается отвязка, может быть флаг или просто удалять запись из messenger_links.

Безопасность, подписи, проверки:

Проверка подлинности сообщений от мессенджера: В Telegram webhook вы можете указать secret_token при setWebhook, тогда Telegram будет присылать заголовок X-Telegram-Bot-Api-Secret-Token с этим значением. Это полезно, чтобы убедиться, что запрос действительно от Telegram, а не от третьих лиц. MAX, насколько известно, не поддерживает кастомный секрет при webhook. Поэтому для MAX можно сверять User-Agent или IP-адреса (возможно, в будущем VK предоставит диапазоны) либо делать нестандартный URL webhook (с случайным UUID в пути, чтобы его не угадали). В любом случае, ваш /webhook endpoint должен проверять валидность полученных данных: например, в MAX в update приходит поле chat_id и т.д., соответствующие вашим ботам. Совсем подделать вызов сложно, если не знают токен, но осторожность не помешает.

CSRF и защита бекенда: Учтите, что мини-приложение работает как обычный веб-клиент. Если вы используете cookies для сессии, включите флаг SameSite=None; Secure для поддержки работы внутри WebView. Классического CSRF меньше риск (домен специфичный), но лучше иметь токены или проверять Origin/Referer на ваших callback-методах. Например, /auth/tg/callback должен принимать только запросы из вашего WebApp, а не откуда-то ещё.

Привязка сессии: Если WebApp запускается внутри Telegram/MAX, злоумышленник теоретически мог украсть initData (например, если устройство заражено) и попытаться воспроизвести запрос позже. Поэтому, помимо проверки подписи, стоит убедиться, что auth_date свежий. Также можно внедрить одноразовый nonce: например, передавать в startapp ссылке уникальный код сессии, который сверять. Но чаще достаточно однократной проверки hash + ограничения времени (скажем, 5–10 минут).

Хранение токенов: Bot Token (и Telegram, и MAX) – это чувствительные секреты. Их нельзя включать в клиентский JS. Храните токены на сервере (в .env или секрет-хранилище) и используйте только при запросах к API. Если вы используете вебхуки, URL не должен содержать токен (Telegram раньше требовал, теперь поддерживает secret_token в заголовке или ничего). MAX вообще убрал токен из URL, требуя только заголовок.

Шифрование связи: Очевидно, все взаимодействия должны идти по HTTPS: и вебхуки, и обращение WebApp к вашему серверу. Это требуется и Telegram, и MAX. Если вы на dev-этапе, можно запускать ngrok для HTTPS туннеля. MAX допускает самоподписанные сертификаты для вебхуков (в доке не явно, но указано, что HTTPS, включая самоподписанные), хотя лучше использовать правильный. Telegram вебхук – нужен валидный сертификат или вручную загруженный самоподписанный (метод setWebhook позволяет).

Секция 3 — Пошаговое руководство по реализации (MAX)

1. Регистрация и настройка бота в MAX: Если у вас уже есть бот и мини-приложение в кабинете MAX – пропустите создание. В общем случае, нужно иметь верифицированную организацию в MAX (требование: юрлицо РФ). Затем через интерфейс партнёра создаёте чат-бот: задаёте название, уникальный ник (обязательно оканчивается на bot), описание, иконку. После модерации (до 48 часов) бот появится в каталоге, и вы получите токен. Альтернативно: можно было использовать @MasterBot внутри MAX – аналог BotFather. В MasterBot-е команда /create создаёт бота, /get_token – выдаёт токен, /set_app – привязывает мини-приложение к боту. Убедитесь, что токен сохранён в вашем бекенде. На стороне MAX-платформы привяжите URL мини-приложения: в кабинете организации в разделе «Чат-бот и мини-приложение → Настроить» вставьте HTTPS-ссылку на ваше приложение и сохраните. Выберите тип кнопки (например «Открыть» – это подпись кнопки внутри чата). После сохранения в чате бота в MAX автоматически появится кнопка для запуска вашего приложения.

2. Реализация WebApp (мини-приложения) MAX: Ваше фронтенд-приложение должно подключить скрипт MAX Bridge и правильно обрабатывать начало сессии. Минимальный HTML-шаблон:

<html>
  <head>
    <script src="https://st.max.ru/js/max-web-app.js"></script>
    <script>
      window.addEventListener('DOMContentLoaded', () => {
        WebApp.ready();
        // ... доп. инициализация
      });
    </script>
  </head>
  <body>Ваш интерфейс</body>
</html>


Метод WebApp.ready() сообщит клиенту MAX, что интерфейс отрисован, и уберёт экран загрузки. Вы можете настроить кнопку «Назад» мессенджера: WebApp.BackButton.show() и обработчик на onClick (например, чтобы закрыть приложение). Чтобы прочитать данные пользователя, сразу после загрузки можно использовать:

const initData = WebApp.initDataUnsafe;
console.log("User", initData.user);


Здесь initData.user.id – ключевой идентификатор. На клиенте не выполняйте проверку hash (ведь у вас нет BotToken здесь), но можете отправить всё на сервер. Обычно мини-приложение делает AJAX-вызов:

fetch('/auth/max/callback', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ initData: WebApp.initData })
});


На сервере реализуйте логику приёма: достать initData, проверить по алгоритму, идентифицировать пользователя. Верните ответ (например, JSON {authorized: true, user: {...}}). После этого можете показывать в UI: «Здравствуйте, Имя!» и основную функциональность. Если нужен номер телефона – вызовите WebApp.requestContact(), а затем в вебхуке бота отловите событие message_new с типом contact. Однако, есть особенность: requestContact() в MAX открывает нативный диалог в приложении MAX, и после подтверждения контакт придёт боту сообщением, а не напрямую в WebApp. Т.е. ваш бот получит update с типом contact_shared (возможно, как часть message), содержащий номер. Поэтому, чтобы не усложнять, лучше сразу доверять идентификации по user.id и не требовать телефон, если не критично.

3. Подключение вебхука или лонг-пуллинга: Настройте получение событий от MAX. Для разработки проще сразу использовать Webhook. Убедитесь, что у вас есть публичный HTTPS endpoint (например, https://yourdomain.com/max-webhook). Затем сделайте запрос:

POST https://platform-api.max.ru/subscriptions
Headers: { Authorization: <ваш_токен>, Content-Type: application/json }
Body: { "url": "https://yourdomain.com/max-webhook" }


Если запрос успешен, MAX привяжет ваш вебхук. Можете проверить: GET https://platform-api.max.ru/subscriptions вернёт текущий URL. На вашем сервере endpoint /max-webhook должен принимать POST JSON. Например, событие о новом сообщении от пользователя выглядит примерно так:

{
  "type": "message_new",
  "object": {
    "message": {
      "text": "/start",
      "chat": { "chat_id": 12345, ...},
      "from": { "user_id": 67890, "first_name": "Ivan", ...}
    }
  }
}


Точный формат смотрите в документации (объект Update). В ответ немедленно возвращайте 200 OK. Отладка: чтобы протестировать, отправьте своему боту сообщение из приложения MAX (например, напишите «ping»). Ваш /max-webhook должен логировать событие. Если не приходит – проверьте, что вебхук успешно зарегистрирован и ваш сервер доступен. (Совет: на этапе разработки можно использовать GET /updates вместо вебхука, опрашивая раз в несколько секунд, но не забудьте отключить webhook перед этим: DELETE /subscriptions.)

4. Отправка пробного сообщения (Hello World): Теперь проверим отправку сообщений пользователю. Предположим, вы сохранили chat_id пользователя, который открыл мини-приложение (это можно получить либо из initDataUnsafe.chat.id, либо из вебхука /start). На вашем сервере вызовите метод отправки:

POST https://platform-api.max.ru/messages
Headers: { Authorization: <token>, Content-Type: application/json }
Body: { "chat_id": <число>, "text": "Привет из бота!" }


Если chat_id правильный (и пользователь действительно запустил бот), вы получите ответ 200 с JSON сообщением, а пользователь увидит новое сообщение в MAX. Если чат недоступен (например, пользователь удалил бот), API вернёт ошибку 400/404. После этого базовая связка проверена.

5. Механизм привязки аккаунта и выдачи уведомлений: Реализуйте на сервере логику из архитектуры: сохранение messenger_links. Когда /auth/max/callback срабатывает впервые для данного пользователя MAX, создайте запись с его max_user_id и chat_id. Верните фронтенду флаг, что подписка на уведомления возможна. В интерфейсе мини-приложения отобразите, например, переключатель «Получать уведомления». При изменении его состояния вызывайте ваш API (/max/subscribe?enabled=true). На сервере обновляйте поле is_notifications_enabled. Если включается – сразу отправьте подтверждающее сообщение (как выше). Когда в вашем основном приложении происходит событие, дергайте функцию отправки уведомления этому chat_id.

6. Особенности и распространённые ошибки (MAX):

Валидация initData: как отмечалось, обязательно реализуйте проверку подписи. В противном случае модерация отклонит мини-приложение. Плюс, вы рискуете безопасностью. Убедитесь, что используете именно алгоритм из доков MAX (с префиксом "WebAppData"). Телеграмовский алгоритм похож, но там секрет = SHA256(token), а у MAX – HMAC с "WebAppData"+token. Не спутайте.

Отсутствие https или неверный URL: если мини-app не грузится, проверьте, что URL в кабинете организации точь-в-точь совпадает с вашим (включая пути). Часто ошибка – забыть слэш в конце или использовать http. MAX поддерживает только HTTPS.

Проблемы с вебхуком: если POST /subscriptions возвращает ошибку, возможно, у вашего бота уже включён long polling. Нужно либо вызвать DELETE /subscriptions перед повторной привязкой, либо проверить, не активен ли webhook у другого бота на тот же URL. Также убедитесь, что ваш сервер возвращает статус 200 быстро. MAX может отключить вебхук, если получает ошибки или таймауты.

Неправильная отправка токена: начиная с августа 2025, MAX не принимает токен в query-параметрах или теле – только в заголовке Auth. Если вы использовали старый метод, исправьте.

Отправка сообщений без контекста: убедитесь, что chat_id взят верно. Если пользователь только открыл мини-app, chat_id можно взять из WebAppData (initDataUnsafe.chat.id). Если его там нет (в редких случаях), возможно, бот не в чате – тогда сообщение не дойдёт. Обычно сам факт открытия означает, что чат создан.

Кнопка «Назад» не работает: если нужно, чтобы пользователь мог закрыть мини-app, используйте WebApp.BackButton. На мобильном клиенты MAX показывают её в заголовке. Или предоставьте кнопку внутри интерфейса, вызывающую WebApp.close().

Модерация и требования: не забудьте, что MAX требует встроить страницы «Пользовательское соглашение» и «Политика конфиденциальности» непосредственно в интерфейс мини-приложения или бота. Обычно в меню вашего приложения делаете ссылки или раздел. Также запрещён определённый контент (18+, экстремизм и пр.). Если нарушение – не пропустят.

Локализация хранения данных: если пока используете зарубежный хостинг (Vercel, Neon и т.д.), это не помешает запуску, но для соответствия закону данные пользователей (например, телефоны, которые вы сохраняете) должны в проде храниться на территории РФ. Планируйте миграцию на российский сервер (Yandex Cloud, Selectel, etc.). В самих доках MAX прямо указано, что можно пользоваться Vercel для хостинга фронта, но про базу данных позаботьтесь отдельно.

Секция 4 — Пошаговое руководство по реализации (Telegram)

1. Создание бота и получение токена: Используйте официальный бот @BotFather. Последовательно отправьте команды: /newbot (дать имя отображаемое и юзернейм бота), BotFather выдаст токен вида 123456:ABC-.... Сохраните его. Настройте основные поля: описание (/setdescription), картинку (/setuserpic), а главное – Main Menu или Web App:

Если вы планируете запускать мини-приложение через кнопку в профиле бота, выполните /setbotmenu → выберите тип “Launch Web App” и укажите URL вашего приложения. BotFather попросит домен (по правилам Telegram, вы должны сначала привязать домен через /setdomain, если он ещё не привязан). Укажите тот же домен, где хостится ваше приложение. После этого у бота в профиле появится большая кнопка «Запустить приложение».

Также вы можете настроить прямую ссылку (для сайта вы это сделаете вручную). Telegram поддерживает формат https://t.me/<bot>?startapp=<param> для открытия основного Web App бота. Чтобы она работала, у бота должна быть настроена Main Web App (как выше). Альтернативно, Telegram позволяет несколько Web App: например, можно отправлять inline-кнопки с web_app привязкой (для разных разделов). Но в нашем сценарии достаточно основной.

2. Настройка вебхука для бота: На вашем сервере создайте endpoint /telegram-webhook (например). Затем вызовите через cURL или библиотеку:

POST https://api.telegram.org/bot<Токен>/setWebhook
Content-Type: application/json
Body: { "url": "https://<вашдомен>/telegram-webhook", "secret_token": "<случайная строка>" }


Вы получите {"ok":true} если успех. Теперь Telegram будет слать обновления на этот URL. На стороне сервера в обработчике проверьте заголовок X-Telegram-Bot-Api-Secret-Token – он должен соответствовать заданному (например, сохраните "secret_token": "MySecret123" и сравнивайте). Это защитит от посторонних. При поступлении JSON обновления (update_id, message или callback_query и т.д.) логируйте их и отвечайте HTTP 200 без тела.
Примечание: Если вы не хотите вебхук, можно опрашивать: не вызывайте setWebhook, а делайте периодически GET /getUpdates. Для production это менее надёжно, поэтому рекомендуется вебхук.

3. Реализация Telegram Web App фронтенда: Ваше веб-приложение должно включать скрипт Telegram:

<script src="https://telegram.org/js/telegram-web-app.js"></script>


Этот скрипт даст объект window.Telegram.WebApp. Как и в случае с MAX, на загрузке можно вызвать:

Telegram.WebApp.ready();


чтобы Telegram знал, что UI отрисован. Telegram WebApp API также позволяет настроить цвет темы (например, WebApp.setHeaderColor('bg_color')), показывать кнопку настроек, всплывающие уведомления и прочее – при необходимости используйте. Для начала, получите initData:

const initData = Telegram.WebApp.initData || '';


и отправьте на сервер для проверки. Серверный код проверки: как описывалось, собрать параметры, секрет = SHA256(token) и сравнить hash. После успешной проверки – логин/регистрация пользователя (см. шаги ранее). Отправьте фронту ответ (например, JSON с профилем или сессионтокеном). Теперь можно приветствовать пользователя:

const user = Telegram.WebApp.initDataUnsafe.user;
document.getElementById('hello').innerText = `Привет, ${user.first_name}!`;


Если вам нужен более сложный вход (например, привязать к существующему аккаунту вашего сервиса) – запросите, например, email или ID, или предоставьте кнопочку «Связать с другим аккаунтом». Но обычно Telegram-достаточно. Важно: Telegram initDataUnsafe содержат user.id, которого достаточно, чтобы уникально идентифицировать TG-пользователя. Связывать по номеру телефона не всегда надёжно (пользователь может скрывать телефон). Лучше использовать именно ID, а для отображения – username (если есть). Номер телефона можно запросить через отдельный процесс: например, попросить пользователя нажать кнопку «Отправить телефон», которую бот должен послать как KeyboardButton. Вы не можете вызвать requestContact из WebApp, поскольку Telegram WebApp JS API не имеет такой функции (в отличие от MAX).

4. Получение chat_id и разрешение на сообщения: В Telegram chat_id для личного чата равен user_id (для большинства пользователей – это просто их ID). Получить chat_id можно на стороне сервера из входящего update. Когда пользователь нажал Start, в вашем webhook-прилёт сообщение:

{ "message": {
    "chat": { "id": 123456789, "type": "private", ...},
    "from": { "id": 123456789, ...},
    "text": "/start ..."} }


Здесь chat.id – это и есть нужный chat_id. Сохраните его вместе с user_id (в случае приватного чата они равны). Если по каким-то причинам webhook недоступен (бывает, при разработке), можно использовать Telegram.WebApp.sendData из WebApp, но это работает только если WebApp открыт с клавиатуры/inline кнопки, а при direct link – не работает. Поэтому рекомендуется: полагаться на то, что Start был нажат, и chat_id известен. Ваш backend, после обработки /auth/tg/callback, может отправить сразу сообщение приветствия с помощью Bot API (в ответ на /start, или отдельно). Этот первый ответ сам по себе подтвердит работу. Пользователь фактически разрешил общение нажатием Start, так что дополнительного разрешения не требуется. Тем не менее, хорошей практикой является явно указать в интерфейсе: «Бот будет присылать вам уведомления». Можно добавить кнопку «✅ ОК» внутри WebApp, которая вашим сервером расценится как окончательное согласие. Но технически это не обязательно – уже можно слать. Если же бот был открыт через inline-режим или другого чата, ситуация другая (но у нас – прямой).

5. Отправка тестового сообщения (Hello World): После успешного входа, как только вы сохранили chat_id, попробуйте отправить сообщение. Прямо в коде сервера или через API-вызов:

POST https://api.telegram.org/bot<Токен>/sendMessage
Body: { "chat_id": <id>, "text": "Привет из Telegram WebApp!" }


Должен вернуться {"ok": true, "result": {...}}. Пользователь увидит в Telegram сообщение. Таким образом проверяем, что связка работает. Обычно такое сообщение можно отправлять либо автоматически сразу после /start (в коде обработчика webhook), либо по нажатию кнопки «Enable notifications» в WebApp, как описано.

6. Завершение и дальнейшие шаги: WebApp можно закрыть вызовом Telegram.WebApp.close() – обычно вы делаете это, когда уже не нужен никакой результат от пользователя. Например, после того как он залогинился и включил рассылки, можете показать кнопку «Готово» – по нажатию закрыть. Бот при этом остаётся в списке чатов. Далее, реализуйте логику рассылки как описано: по событиям вашего сервиса дергать sendMessage с соответствующим текстом и chat_id, полученным ранее. Убедитесь, что обрабатываете ошибки API (например, 403 – бот заблокирован). Telegram API также имеет метод getChat – можно использовать, чтобы проверить существует ли чат с пользователем (но если бот заблокирован, getChat тоже не достучится).

7. Частые проблемы и их решения (Telegram):

WebApp не запускается по ссылке: если при клике на t.me/…?startapp ничего не происходит, убедитесь, что у бота настроен Main Web App через BotFather. Без этого параметра startapp ссылка может игнорироваться (или открываться просто чат без запуска приложения). Также проверьте, что у пользователя обновлён клиент Telegram (поддержка mini app появилась в версиях ~2022 года).

Пользователь не нажал Start: в случае, если пользователь открыл Telegram, но не нажал кнопку Start, WebApp не запустится, и бот не получит ID. В веб-версии Telegram может сразу открыться приложение, но на мобильных требуется действие. Решение: в тексте лэндинга или инструкции явно скажите «Нажмите "Start" в Telegram, чтобы продолжить».

Ошибка проверки hash: если ваша серверная валидация не проходит – убедитесь, что правильно реализовали алгоритм. Часто ошибки: забывают один из параметров или сортируют неправильно, или используют неверный секрет. Помогает отладка: в Telegram можно временно вывести Telegram.WebApp.initData на экран, скопировать на сервер и сравнить расчёт шагов. Помните, секрет = SHA256(bot_token) (в MAX было иначе).

Webhook не получает обновления: проверьте, что вы ответили 200 OK на предыдущее обновление. Telegram, если получает ошибку, может прекратить отправку. Также посмотрите метод getWebhookInfo – он покажет состояние. Возможные проблемы: неправильный сертификат, неверный URL. Если всё сложно – на время можно отключить webhook (setWebhook с пустым URL) и воспользоваться getUpdates (вызвать вручную через curl для проверки).

Не приходит username/phone: Telegram может не установить username у пользователя (это опционально). Не рассчитывайте на него как на уникальный ключ. Лучше user.id. Телефон не приходит сам – его нужно явно запросить у пользователя через обычный бот (не WebApp). Можно, кстати, встроить процесс: если вам критически нужен телефон, то в WebApp после логина покажите инструкцию «Нажмите кнопку ниже, чтобы отправить телефон», а бот заранее прислал KeyboardButton. Когда пользователь поделится контактом, ваш webhook получит message.contact. Вы можете сразу связать этот номер с аккаунтом.

Ограничения размеров: Telegram Web App initData помещается в URL фрагмент при передаче клиент→веб. Он достаточно компактный, но если в start_param вы пытаетесь передать большой JSON (>512 символов), Telegram отбросит start_param. Планируйте укладываться в лимит (например, используйте короткие кодированные строки, если нужны). MAX аналогично имеет лимит 512 символов.

Секция 5 — Что реализовать в первую очередь (чек-лист MVP)

Настройка инфраструктуры:
a. Зарегистрируйте Telegram-бота через BotFather и получите токен. Зарегистрируйте MAX-бота через кабинет VK (после получения доступа) или через @MasterBot – получите токен.
b. Настройте основное мини-приложение для каждого бота: в MAX – привяжите URL в кабинете организации; в Telegram – через BotFather (/setdomain и /setbotmenu указав URL). Убедитесь, что кнопка запускается в мессенджерах.

Разверните простой бекенд с HTTPS: Ваш сервер должен быть доступен по HTTPS из интернета. Для начала можно использовать сервисы типа Heroku, Fly.io или цикл с ngrok для локального сервера. Важно иметь валидный SSL. Настройте маршруты: /webhook/max, /webhook/tg (пока можно просто логировать входящие). Пропишите в коде ваш Bot Token’ы.

Установка вебхуков: Используя токены, вызовите API:

MAX: POST /subscriptions с вашим /webhook/max URL.

Telegram: setWebhook для /webhook/tg (плюс секрет).
Проверьте (через GET /subscriptions и getWebhookInfo) что вебхуки активны.

Мини-приложение (frontend): Создайте простую страницу (например, на React или просто HTML/JS) по URL, указанному в ботах. На страницу подключите telegram-web-app.js и max-web-app.js (можно только нужный, но если объединено – учитывайте окружение). Реализуйте вывод хотя бы user.first_name из initDataUnsafe. Сделайте кнопку «Включить уведомления» (пока без функционала). Хостинг – Vercel (упрощенно, как советует VK). Убедитесь, что страница грузится по прямой ссылке.

Верификация initData (backend): Напишите функцию для проверки подписи Telegram и MAX. Протестируйте её с образцом данных (например, снимите параметры при открытии вашего мини-app в Telegram Desktop, где можно скопировать URL фрагмент). То же для MAX: можно взять WebApp.initData и проверить. Убедившись в корректности, интегрируйте в обработчик /auth/tg/callback и /auth/max/callback. Пока можете просто возвращать «ok» или сессионный идентификатор.

Привязка данных и база: Настройте базу (PostgreSQL/MySQL или даже in-memory) с таблицами users и messenger_links. Когда приходит новый user_id из TG или MAX, создавайте запись пользователя (минимум id) и запись messenger_link (с соответствующим provider, user_id, chat_id). Можно сделать user_id автогенерируемым, а messenger_link хранить оба ID. Если пользователь приходит повторно – находите существующую запись (по provider_user_id). Теперь ваш бекенд «знает», к какому локальному пользователю относится Telegram ID 1234 или MAX ID 5678.

Включение уведомлений (end-to-end): Сделайте так, чтобы на нажатие кнопки «Включить уведомления» фронтенд вызывал ваш бекенд (/notify/enable например) с указанием messenger (или на конкретном endpoint). Сервер по user_id находит messenger_link и ставит is_notifications_enabled = true. В ответ фронту отдайте успех. Затем сразу отправьте тестовое сообщение пользователю:

MAX: POST /messages «Вы подписаны на обновления».

Telegram: sendMessage с аналогичным текстом.
Появление этих сообщений у пользователя будет финальным подтверждением.

Валидация сценария: Протестируйте полный цикл: с телефона откройте сайт → нажмите «Telegram» → Telegram открылся, бот стартован, Web App показался → на бекенд пришёл /start (в логе webhook) и запрос на /auth/tg (в логе) → в базе создался пользователь → нажмите кнопку в вебаппе → бекенд обновил статус, бот прислал сообщение. Затем попробуйте с MAX (если у вас есть доступ к MAX): откройте MAX (или web.max.ru), найдите бота (или через ссылку), откройте → мини-app → то же самое.

Улучшения (после MVP): Добавьте обработку ошибок и UX: например, если пользователь в Telegram не нажал Start, ваш WebApp может показывать сообщение «Пожалуйста, запустите бота, затем обновите страницу». Добавьте в интерфейсе ссылки на «Политику конфиденциальности» и «Пользовательское соглашение» (можно скрыть в меню). Реализуйте команду /stop для бота, чтобы пользователь мог отписаться (ваш webhook поймает /stop или «/start stop_payload» и тогда вы выключите is_notifications_enabled).

В плане сложности: интеграция Telegram сравнительно проще, много примеров и более либеральные требования. MAX сложнее из-за требований к организации и модерации, плюс платформа новая – возможны баги. Наибольшие неизвестные могут быть связаны с тем, как MAX поведёт себя с новыми пользователями и нужно ли дополнительное одобрение. Начните с разработки Telegram части (для отладки бизнес-логики), затем адаптируйте под MAX, тщательно читая русскоязычные источники и официальный dev.max.ru.

Финальный дайджест: план действий и ссылки

Шаг 1. Создайте и настройте ботов: зарегистрируйте бота MAX через кабинет VK (требуется юрлицо), получите токен; создайте Telegram-бота через BotFather. Привяжите к ним мини-приложения: в MAX добавьте URL приложения, в Telegram установите Main Web App через BotFather.

Шаг 2. Разработайте мини-приложение (Web App): это обычное веб-приложение (HTML/JS) с подключением API мессенджеров. Используйте max-web-app.js для MAX и telegram-web-app.js для TG. Извлекайте initDataUnsafe чтобы получить user.id и др. Пошаговый код в доках: в MAX сразу вызывайте WebApp.ready(), в TG – Telegram.WebApp.ready(). Ресурсы: MAX Bridge документация, Telegram Mini Apps гайд.

Шаг 3. Проверьте безопасность: подписи initData: реализуйте на сервере алгоритм проверки HMAC для Telegram и MAX. Смотрите официальные доки: MAX WebApp валидация, Telegram Login Widget/WebApp проверка. Без этого нельзя запускаться – убедитесь, что сервер отвергает недостоверные данные.

Шаг 4. Включите получение обновлений (Webhook): подключите вебхуки для обоих ботов. MAX: вызовите POST /subscriptions с вашим HTTPS URL. Telegram: вызовите setWebhook с URL и секретом. Обработчики должны быстро отвечать 200 OK и разбирать входящие сообщения (например, команда /start). Документы: примеры кода webhook MAX, описание Telegram webhook.

Шаг 5. Сохраните связь аккаунтов: на бэкенде, после успешной проверки initData, привяжите messenger ID к пользователю вашей системы. Создайте запись с полями user_id, messenger (MAX/TG), messenger_user_id, chat_id. Это позволит вашему приложению знать, кому слать уведомление. Например, храните chat_id = user.id для Telegram и chat.id (из initData) для MAX.

Шаг 6. Реализуйте отправку сообщений: с серверной стороны, используя сохранённые chat_id и токены, отправляйте уведомления:

Для MAX: HTTP POST на platform-api.max.ru/messages с JSON {"chat_id":..., "text":"..."}:contentReference[oaicite:149]{index=149}.

Для Telegram: метод sendMessage через API URL или с помощью SDK.
Убедитесь, что бот может писать (пользователь нажал Start / открыл бот). Лимиты: MAX до 30 сообщений/сек, TG – 30 сообщений/сек глобально, ~20 сообщений/мин на чат.

Шаг 7. Тест и отладка сквозного сценария: пройдите как пользователь: сайт → открыть мессенджер → войти → подписаться → получить сообщение. Логируйте каждый этап (в вебхуке, в auth callback, при отправке). Используйте тестовые данные: можно временно отправлять себе сообщения командой /start, смотреть что приходит. По итогам теста устраните проблемы (например, не приходит update – проверить webhook, не отправляется сообщение – проверить chat_id и токен).

Шаг 8. Подготовьтесь к релизу: для MAX – проверьте соответствие требованиям (юридические страницы, контент) перед подачей на модерацию. Для Telegram – убедитесь, что бот заполнен (описание, меню команд). Настройте обработчики на /start, /help – чтобы бот не выглядел пустым.

Полезные ссылки:

MAX официальная документация: MAX Bridge и Web Apps, Пример проверки данных, Bot API методы (отправка сообщений, вебхуки).

Статья Хабр о изменениях в MAX (2025) – подробно о токенах, доменах API, требованиях.

Telegram официально: Bots Web Apps (core.telegram.org) – содержит описание запуска мини-приложений и initData, Login Widget – процесс и проверка подписи.

Практический туториал по Telegram Mini Apps (Habr) – советы по авторизации и особенностям.

Следуя этому плану, вы получите рабочую интеграцию: пользователи смогут заходить через MAX или Telegram, а вы – связывать их аккаунты и отправлять им автоматические уведомления в любимом мессенджере. Успехов!
